# Octane expert: decisions

What's already decided for `@ui-sdk/octane`, so a review doesn't raise it again.

Last reviewed: `0718f402` (2026-11-20, the whole branch against `b4dbe882`: every component, the server-render pipeline and the fork-only CI).

Mirrors `packages/react` at `f8f33019`. Each upstream commit after it that touches a file Octane has ported, or a ported component's React fixture, is ported too, and this line moves to it. Commits that need nothing are listed below.

Upstream commits before `b4dbe882` that needed nothing in Octane, from the replay that brought the port up from `@ui-sdk/react@0.1.0-beta.1`:

- `c0a383f9` (#501): resolves React's Flight lazy placeholder in `render` elements. Octane has no Server Components, and its own `lazy()` returns an ordinary component, so `cloneElement` already works.
- `92653572` (#675): empties `followTree`'s list of detached elements once a popup unmounts, since React keeps the unmounted fiber, whose ref reaches the list, for a while. Octane keeps nothing of an unmounted component: without the change, a popup's element was collected right after unmount in dev and production compiles. After unmount the list is reachable only through one of its own elements, whose descriptor Octane keeps on the node.
- `9b0f80fc` (#682): `resolveLazy` unwraps every lazy wrapper, since `next dev` nests the Flight placeholder two deep. Octane never ported `resolveLazy` (see `c0a383f9`), so there's nothing to change.

## Settled

- **A port of `@ui-sdk/react`, file for file.** Same names, exports, JSDoc and stability labels, so every file diffs against React's. Octane-only APIs and `.tsrx` stay out.
- **`import * as React from "octane"`.** Kept as `React` so the namespace calls match React's files line for line, as Octane's own Base UI port does.
- **Source ships, not a build.** Every `.tsx` opens with the octane pragma and the package peers on `octane >=0.20.0`. An open lower bound like `@ui-sdk/react`'s `react >=19`, since Octane's 0.x minors break often and a caret range would fail installs. The nightly canary catches what the open range lets through.
- **`<Ctx value>` for every context.** Octane removed `.Provider`. Lowercase locals that hold a context are renamed to a capital before rendering.
- **One `useId` per root.** Per-slot ids derive from it (`${id}-${key}`), since Octane rejects a hook inside a loop.
- **`null` deps on effects that run every commit.** Octane infers omitted deps. The `runBindWrites` effect in `usePrimitive` captures only an import, so omitted deps infer `[]` and only the mount gets flushed: `act-mount.test.tsx`'s later-commit case fails without `null`. `usePlacedContent`'s layout effect (#1019) passes `null` too, since React runs it every commit. Omitted, its deps infer `[wanted, seen]`, which passes the same tests.
- **`onInput` for core's `input` event and the controlled-value no-op.** Native events go to core as they are.
- **`propNames`, `booleans` and `styleObject` stay.** A style string would replace the inline styles core writes itself.
- **Hooks never inside JSX children.** All 22 `{usePart(...)}` sites in React's 17 files call `usePart` into a `const` first. See "Known and open" for why.
- **`descriptorChildren` on `Menu`, `Select`, `Combobox`, `TreeItem`, `TriggerMenu`, `Autocomplete` and `Command`, and on the four item texts that mark matches.** As a top-level `const` with a named import, the only form the compiler reads. An unmarked item text in a `.tsrx` app's own component shows the item's value; `scripts/package-consumers/octane-tsrx` checks all four. Not on `Field`: it clones its `render` prop, and props keep descriptors.
- **`isRenderFunction(children)`, never `typeof children === "function"`.** On Octane's production compile path, children like text written inside a `.map()` (`<Part>Tip {tip}</Part>`) arrive as a compiled children block, a function that isn't a render function of state. Calling it crashed the `forms` and `tooltips-perf` fixtures (`reading 'block'`). Vitest compiles the dev path, so only built-playground specs catch it. The helper in `render-element.ts` adds `!isChildrenBlock(children)`.
- **Children typed `{} | null | fn`.** Octane's `ReactNode` is `unknown`, so `ReactNode | fn` would erase the function's state type.
- **`useState` destructured before passing on.** It returns three items in Octane.
- **No `Profiler` in fixtures.** Only React's spec reads the commit counter it fed.
- **`IS_REACT_ACT_ENVIRONMENT` turns on the act warning, as in React's tests.** Octane reads React's global. `setIsOctaneActEnvironment` left the public `octane` entry in 0.22.0 for `octane/internal/client`, which isn't API, so `act-mount.test.tsx` sets the global as React's file does.
- **`shimMissingExports` for the Octane server bundle only** (`apps/playground/ssr-plugin.ts`). Every `octane.tsx` fixture exports `mount`, which imports `createRoot`, and `octane/server` has no `createRoot` (still none in 0.27.0). The server never calls `mount`, so the shim's `undefined` is never read; splitting `mount` out of every fixture would diverge them from React's.
- **Octane-only prop shapes in the merge path.** `mergeProps` merges a style written as text through `styleObject` and passes class values on as an array for Octane to compose; `mergeRefs` flattens ref arrays; `yieldToAuthor`'s check reads the DOM spelling too (`autocomplete`). React has none of these shapes, so these lines don't diff against React's. `test/octane-props.test.tsx` covers them.
- **`Command`'s `typeof children !== "function"` checks stay.** A children block skips `hasChild`, but a placed `CommandList` still registers through `Placed` when it mounts, so no second list renders; a production probe matched React.
- **`octane.spike.spec.ts` runs on every project.** Only Octane has the `tree-children` fixture, so the others skip it.
- **`private: true` and no framework docs pages.** The package stays unpublished until its docs phase; `package-docs.ts` sets `octane: undefined` until then.
- **`octane-tsrx` runs the specs against `.tsrx` fixtures** (`fixtures/<name>/octane-tsrx.tsrx`), written as a `.tsrx` author would: `@{ }` templates, `@for` with keys, `@if`, rows as components. They export what `octane.tsx` exports. `.tsrx` files format with `oxc-tsrx-fmt` (`.oxfmtrc.json` mirrors `.prettierrc`) and typecheck with `oxc-tsrx-lint --type-check`; ESLint can't parse them.
- **`requireDirective` in the shared playground.** Octane's Vite plugin has no include option, and without it would compile every `.tsx`, React's and Solid's fixtures included.

- **`octane-portal` leaves out `menu.spec`'s shadow-root click test.** With the trigger moved into a shadow root and the content portaled to `#portal-root` outside it, the content's `aria-labelledby` can't reach the trigger, so the menu has no name and `getByRole("menu", { name: "File" })` finds nothing. The menu does open and stay open. Vue's portaled menu is unnamed the same way; no upstream project runs the pair, since React skips the test and only React has a portal project.

- **Octane runs passive effects after paint, even for a discrete event or `flushSync`** (Octane's `docs/differences-from-react.md`, scheduler). A React regression test for a `flushSync` timing bug may pass on Octane without its fix: `select-search-flush-sync` (#935) guards the behaviour on Octane but wouldn't catch the bug returning.
- **`tree-hydration` (#1147) passes on Octane without core's fix.** Octane hydrates without yielding, even inside `startTransition`: a probe logged `Slow` and its next sibling rendering before `hydrateRoot` returned, and a 0ms timeout and a `MessageChannel` task only after. No render drops an ancestor's props before its items read them, so the test guards the depth but wouldn't catch the bug returning; React's fails without the fix, with the third item at level 2. It keeps React's `Slow`, so it catches the bug if Octane starts slicing hydration.
- **`popover-suspense-trigger` (#1229) passes on Octane without core's hydration fix.** It guards the id a trigger's bind sets when hydration kept the server's attributes. React renders the Suspense boundary the server couldn't finish after the rest hydrates, so `Account` binds first without the id, and React's test fails when only that `el.id` line is gone (it passes with the whole fix reverted). Octane renders the boundary in the same pass, in tree order: a probe logged its child rendering, then its next sibling, both before `hydrateRoot` returned. `Profile` binds first and `Account` takes the id when it opens, so the port passes either way. It keeps React's lines, so it catches the bug if Octane starts rendering such a boundary later. The server test in `popover.ssr.test.tsx` does fail without the fix, with 4 trigger ids against 2.
- **`token-input-trigger-menu-aria` (#1286) passes on Octane without core's fix.** It guards a trigger menu written before the editor marking it from mount. React runs each component's layout effects with its refs, in tree order, so a menu before the editor is kept and follows it before the editor's ref binds, and React's "before" case fails without the fix. Octane attaches every ref in a commit before it runs any layout effect: a dev-compile probe of two siblings logged `A ref, B ref, A layout, B layout`, React `A ref, A layout, B ref, B layout`. The menu finds the editor bound in either order, so the port passes either way. It keeps React's lines, so it catches the bug if Octane starts running layout effects between refs.
- **`toast-without-resize-observer` (#1093) collects `onUncaughtError` and expects none.** React's test checks only that the toast shows, since React unmounts the tree when core throws as the toast binds. Octane binds parts in their ref and keeps the tree when a ref throws, so React's lines passed on Octane without core's fix, with the `ReferenceError` only in `console.error`. With the collected errors, the test fails without the fix.
- **`number-input` (#1338) and `date-picker-input-text` (#1356) guard core's reset write on Octane; their other two tests guard only React.** "clearing a field stepped from empty reports null", "clearing a date the app set reports null" and both "typing the text a form reset replaced reports it again" catch edits React's value tracker drops, and pass on Octane with the whole fix reverted, since Octane has none (`knowledge.md`, part 2). `NumberInputControl` and `DatePickerInput` keep their first text as the default, line for line with React, without React's reason in their comments, and the tests drop React's comment on the native setter. Before that line, each "a form reset keeps a controlled field's text with its value" passed without core's write, since an Octane `defaultValue` update moves the reset baseline; with it, the test fails without the write (`"5"` against `"6"`, `"03/14/2026"` against `"04/01/2026"`). The tests keep React's lines, so they catch the bug if Octane starts tracking values.
- **Upstream commits that touch only core or other frameworks need no entry here.** Only commits that touch `packages/react` or a React fixture get ported, a commit that only adds a React test included, and the mirrors line moves to each.

## Unit tests dropped from React's suite

`packages/octane/test` ports every React test file. These cases don't apply to Octane:

- `lifecycle`: "StrictMode's thrown-away instance is never observed, so scope and secrets hold", "StrictMode's thrown-away TriggerMenu never follows the editor" and "an open dialog rendered into a container stays shown through StrictMode's second run of its effects". Octane's `StrictMode` is a pass-through, so no render is thrown away and no effect runs twice.
- `lazy-render`: "a part renders a render element inside two lazy wrappers". That nesting is the Flight client's, and Octane has no Server Components.
- `act-mount`: "a strict mode remount keeps a tab with a button inside it selected". Octane's `StrictMode` doesn't remount.

`value-wrapper-strict-mode` keeps its file but tests a hide and show through `<Activity>`, the unbind and rebind Octane does have.

## Known and open (don't report again, check whether fixed)

Each one rechecked on `octane` 0.27.0 on 2026-11-27, with its repro.

- **Octane miscompiles a hook inside JSX children** (0.20.0, unchanged in 0.27.0). `<Ctx value={v}>{useHook()}</Ctx>` runs the hook in a deferred children body: after the first render its effects disconnect and its state updates never show, with no diagnostic. Repro: a `useCounter` hook rendered inline stays at `0` after two clicks, and its layout effect cleans up and never sets up again; the hoisted form counts to `2`. The port hoists every such call. Report to octanejs/octane; remove nothing until a fixed release ships.
- **`menu.spec` "moving from a submenu trigger straight to another item highlights that item" is load-sensitive.** It failed once at load average 10 to 22 (the item highlighted but didn't take focus), then passed 3 of 3 against a served build.
- **Modal side-effect specs read `inert` and `overflow` once, right after the popup shows, so they fail on a busy machine, on React as often as on Octane.** They include `menu.enhancements` "with modal true, the page scroll is locked…", `popover.enhancements` "modal popovers make the rest of the page inert…" and "live regions keep announcing…", `csp.spec` "a modal dialog locks scrolling…", `dialog.spec` "the rest of the page is hidden from assistive technology", `dialog.enhancements` "the page outside is inert while open…", `agent.security` "the page behind an open modal dialog takes no step…", `presentation.spec` "is modal by default: the page behind is inert…" and `dialog.patterns` "the page around the dialog is inert…" and "persistent elements stay usable…". Most pass when rerun alone. The two `dialog.patterns` tests (`:68`, `:240`) failed most runs in late November even with one worker on a quiet machine, on React too and with or without #1229, so they're an upstream spec timing issue. `csp.spec`'s two (`:83`) failed 18 of 19 runs on 2026-11-27, and every run alone with one worker, on `react` too and with or without #1230. Not an Octane gap.
- **`listbox.picker` "a flick with the mouse coasts past where it let go" is load-sensitive.** It coasted 5 rows against more than 6 once in a 33-minute 4-worker run, then passed 4 of 4 on Octane and on React.
- **The playground's client build takes about 2s longer** (median 8.8s against 6.6s, on 0.20.0) with Octane's plugin loaded, which checks every module for the pragma.
- **`popup.tsx`'s tree-following tracks nothing for a popup that mounts visible.** Octane's portal appends its nodes before `TreeEffect`'s insertion effect runs, so `placed` sees no change and the list holds only the element its ref gave. A portaled popup inside a hidden `<Activity>` still ends up `display: none`, so nothing visible breaks. Recheck with `cached-page`.
- **Octane drops `/* @__PURE__ */` annotations** (0.20.0, unchanged in 0.27.0). `const SelectItemIcon = /* @__PURE__ */ notLabel(...)` compiles to `const SelectItemIcon = notLabel(...)` in a production client compile (`createOctaneCompiler({ environment: "client", dev: false })`), and `ComboboxItemIcon` the same, so every select and combobox page keeps core's `lists/item-icon`, in `pnpm size` and in apps alike. The annotation goes whatever the call's argument is. `scripts/size.mjs` leaves Octane out of `minimalChecked` until a release keeps it. Report to octanejs/octane.
- **Octane hydration keeps mismatched ids, and warns only in a dev compile** (0.20.0, unchanged in 0.27.0). With a different `identifierPrefix`, the client computes new ids and the DOM keeps the server's, as React 19 does. A dev compile (Vitest, the dev server) logs `Octane hydration mismatch` with each attribute, like `id: the server rendered ":s-in-0:", the client ":c-in-0:"`; a production compile, which `vite build` and so every built playground uses, logs nothing. SSR fixtures must hydrate with the same prefix the server used.
- **Octane keeps the tree when a ref callback throws** (0.27.0). The error goes to `onUncaughtError`, or `console.error` without one, and nothing leaves `act()`. Octane's `docs/differences-from-react.md` says an unhandled error unmounts the root's tree, and a throwing `useLayoutEffect` or `useEffect` does. Repro: `<p ref={() => { throw new Error() }}>child</p>` keeps `child` in the container; the same throw in a layout or passive effect empties it. React 19 unmounts for all three. Report to octanejs/octane.
- **Pinned to `octane` 0.27.0, with its exact peer `@tsrx/oxc` 0.24.0.** The newest release old enough for `minimumReleaseAge` on 2026-11-27 (published 2026-11-26T19:49Z); 0.27.1 to 0.27.3 came out on 2026-11-27. Bump then and recheck.

## Fixed in Octane

What the pin to 0.27.0 fixed, each proved on 0.20.0 and on 0.27.0, and the test and fixture workarounds removed with it. The adapter's own source needed nothing: none of its code worked around these.

- **`<Activity>` children threw `props is not defined`** (fixed in 0.23.0). A component whose first parameter wasn't an identifier named `props` compiled a body that read `props`. Repro: a top-level `function A() { return <Activity mode="visible"><Child /></Activity> }`, one with a destructured `{ mode }`, and one with an expression child all threw on 0.20.0 and render on 0.27.0. The `props` parameter and its comment are gone from `cached-page`'s `octane.tsx` and `octane-tsrx.tsrx`, `lifecycle.test.tsx`'s `Hideable` and `concurrent.test.tsx`'s `ActivityTabs`, which now match React's.
- **The scoped children resolver pinned a disposed block** (fixed in 0.23.1 by octanejs/octane#3116). An element with expression children, made once by a parent that outlives a popup, kept the first-opened popup's subtree alive. `leaks.spec`'s 200-open check for menu, combobox and autocomplete failed as expected on 0.20.0 (menu on `octane`, the other two on `octane` and `octane-tsrx`) and passes on both on 0.27.0, where the expected failures failed the run ("Expected to fail, but passed"). The three known gaps are gone, and with them `octaneKnownGaps` and its fixture in `tests/fixtures.ts`.
- **13 shipped declarations imported `"react"`** (fixed in 0.23.1 by octanejs/octane#3117). `pnpm --filter @ui-sdk/octane build` wrote 13 `dist/types` files that import `react` on 0.20.0, and writes none on 0.27.0: `role` is `import("octane").AriaRole`. 0.20.0 exports `AriaRole` too, so the declarations still resolve against the lowest version the peer range allows.
- **`@if` and `@for` blocks were hidden from a part that reads its children** (fixed in 0.24.0 by octanejs/octane#3123). Repro: a marked `Inspect` rendering `<b />@if (shown) { <i /> }{shown && <u />}` saw `b,_frag$0,u` on 0.20.0 and sees `b,i,u` on 0.27.0; a keyed `@for` of two rows went from `_frag$1` to `i,i`. The `.tsrx` fixtures write these as `@if` and `@for` again: `tree`'s `TreeGroup`, `combobox`'s and `autocomplete`'s `?late` content (`@if (late) { … } @else { … }`), and the items that label a closed select or combobox in `rows-perf`, `leaks`, `item-icons` and `select-perf`. With those fixtures on 0.20.0, `octane-tsrx` failed 11 `tree.spec` tests, `select.counts` "a closed select whose label the root found renders no options" at both sizes, and "a content with no children renders items that arrive while it's open" in `combobox.items` and `autocomplete.items`; on 0.27.0 they pass.
- **A JSX element with two type arguments turned off `descriptorChildren` for its whole `.tsrx` module** (fixed in 0.22.0 by `@tsrx/core` 0.6.3, octanejs/octane#3063). Repro: a marked part inside `<Generic<string, boolean>>` saw no children on 0.20.0 and sees `b,i` on 0.27.0. The `select`, `combobox` and `listbox` fixtures write `<Select<string, boolean>>` and the rest again, as `octane.tsx` does, instead of spreading a typed props object. With that on 0.20.0, `select.spec` failed 24 tests on `octane-tsrx`; on 0.27.0 none.
- **A store update committed a sibling inside `@if` after the siblings that follow it** (fixed in 0.23.1 by octanejs/octane#3124). Repro: four siblings that read one store, the first inside `@if`, attached refs `second,third,fourth,first` on 0.20.0 and `first,second,third,fourth` on 0.27.0. `drawer/octane-tsrx.tsrx` renders both backdrops in `@if (parts.backdrop)` again. With that on 0.20.0, `drawer.enhancements` "a settle runs as a spring sampled into linear(), on translate and the backdrop's opacity" failed on `octane-tsrx`; on 0.27.0 it passes.

- **An unnamed menu radio group that inherits a hidden group's choice doesn't re-render** (upstream #1361, React too). When an unnamed group that shows only some of the time hides, core hands its kept choice to the next unnamed group and `forgetOtherPlace` drops it, but the radio group and items select only `radio:${group}`, not the `radio@N` place key, so the next group shows nothing checked until something else re-renders it. Probes failed the same way on React and Octane; core's test reads `partState` directly and misses it. An upstream fix, not this port's.

## Revisit

- Nothing checks that every React test has an Octane twin. Listing `packages/react/test` against `packages/octane/test` shows it; a check could sit beside the export one below.
- Nothing checks that `@ui-sdk/octane`'s named exports match `@ui-sdk/react`'s; `test/exports.test.ts` covers only the package's exports map, so a missed type re-export passes every check. A test comparing the two packages' export names would catch it.
- An inline ref array (`ref={[a, b]}`) is a new array each render, so `mergeRefs` builds a new merged ref and the part detaches and reattaches. `heldRef`'s grace should absorb it; check with bind and unbind counters.
- The canary writes `npm view octane@<v> peerDependencies.@tsrx/oxc` into `pnpm-workspace.yaml` with `sed`. Octane pins it exactly today; a range would need quoting.
- `tests/playwright.octane-fork.config.ts` copies `portalSpecs` from `playwright.config.ts`, which doesn't export it. Keep the two lists in step.
- If a later Octane release proves imported helpers memoizable, `readIn`, `presentIn` and `slotIn` reads may go stale in production builds. The spike's `octane.spike` spec and a production-build run catch it.
